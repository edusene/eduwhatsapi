## 1. VISÃO DO PRODUTO

Crie uma plataforma SaaS própria, inspirada no modelo de infraestrutura de API de serviços como a Datafy API, mas com marca, código, interface e documentação originais. O objetivo é permitir que minha empresa conecte ativos autorizados às APIs oficiais da Meta e disponibilize recursos para vários clientes por meio de um painel e de uma API própria, com chaves internas por cliente, webhooks e gestão multiempresa.

A prioridade inicial é a API oficial do WhatsApp Business Platform / WhatsApp Cloud API. Estruture a arquitetura para permitir adicionar Instagram Messaging API e Messenger Platform futuramente, mas NÃO invente recursos nem implemente integrações que não estejam disponíveis ou autorizadas para o app. Comece pelo WhatsApp e deixe os outros canais desacoplados por adaptadores.

IMPORTANTE: ter acesso de desenvolvedor à Meta não significa automaticamente ter aprovação para todos os produtos, permissões, uso por terceiros ou status de Tech Provider/Partner. Implemente somente os fluxos e recursos compatíveis com as permissões efetivamente concedidas ao app. Não prometa que a plataforma é parceira oficial da Meta, não use selos ou marcas de parceria e não afirme aprovações que não tenham sido concedidas. Deixe a documentação clara sobre os requisitos de App Review, verificação empresarial, permissões avançadas e onboarding de clientes. Não tente contornar revisão, limites, políticas ou controles da Meta.

## 4. FUNCIONALIDADES DO MVP

### 4.1 Autenticação e organizações
- Cadastro, login, logout, recuperação de senha e confirmação de e-mail via Supabase Auth.
- Páginas protegidas: dashboard, canais, credenciais, logs, webhooks e configurações.
- Cada usuário pertence a uma organização/empresa (tenant).
- Suportar organização individual no MVP e deixar estrutura preparada para convidar membros e definir papéis.
- Papéis iniciais: `owner`, `admin`, `developer`, `viewer`.
- Um usuário nunca pode ler, alterar ou usar dados, tokens, números, mensagens, logs ou chaves de outra organização.
- Validar a sessão no backend. Não confiar apenas em verificações JavaScript ou em dados enviados pelo navegador.
- Implementar autorização centralizada e checagem de organização em todas as operações.
- Usar Supabase Row Level Security (RLS) nas tabelas com dados de clientes.
- Nunca expor `SUPABASE_SERVICE_ROLE_KEY` ao frontend. Usar a chave `anon`/publishable no navegador apenas se necessária e apropriada; operações privilegiadas devem ocorrer no backend.
- Não armazenar senha de usuário manualmente. Supabase Auth é responsável pela autenticação.

### 4.2 Painel
Crie uma interface moderna, limpa, profissional e responsiva, com:
- Tela de login/cadastro.
- Dashboard com resumo de canais conectados, números, uso de API e eventos recentes.
- Página de canais/números conectados.
- Página de chaves de API.
- Página de webhooks de saída.
- Página de logs de requisições e eventos.
- Página de configurações e perfil.
- Estados vazios úteis, mensagens de erro claras, feedback de carregamento e confirmações para ações destrutivas.
- Navegação acessível, layout adaptado a desktop e celular.
- Não exibir métricas falsas: quando não houver dados, mostrar zero ou estado vazio.
- Nunca exibir tokens completos depois de sua criação. Mostrar apenas prefixo/sufixo ou máscara.

### 4.3 Conexão oficial com a Meta
Implemente a base para conectar ativos do WhatsApp Business Platform usando somente fluxos oficiais suportados pela Meta.

- Preparar o fluxo OAuth/Embedded Signup oficial quando aplicável e disponível para o tipo de app e permissões aprovadas.
- Não simular o Embedded Signup com uma tela falsa.
- Não pedir a senha do Facebook do usuário.
- Usar `state` criptograficamente seguro para proteção contra CSRF, validar redirect URI e validar a resposta OAuth no servidor.
- Solicitar apenas escopos necessários e documentados. Não assumir que qualquer permissão será concedida.
- Armazenar de forma segura os identificadores e tokens necessários, com criptografia no backend para tokens persistidos, quando aplicável.
- Registrar dados mínimos necessários: identificador da WABA, identificador do número, nome/telefone exibido quando retornado, status de conexão, organização proprietária, timestamps e estado da autorização.
- Não considerar uma conta conectada até que o servidor valide a resposta e consiga confirmar os dados pela API oficial.
- Implementar ações de desconectar/revogar acesso e apagar dados associados quando aplicável.
- Deixar as variáveis de configuração e URLs de callback documentadas.
- Se a configuração externa do app, revisão, permissões ou Embedded Signup ainda não estiver pronta, exibir instruções claras no painel e documentar o que falta. O restante do sistema deve continuar funcionando em modo de desenvolvimento com mocks.

### 4.4 API própria com chaves internas
Crie uma REST API versionada, por exemplo `/api/v1/`, para que cada cliente use a plataforma a partir de n8n, Make, scripts Python ou outros sistemas.

- Gerar chaves internas de API por organização e permitir criar, listar metadados, revogar e rotacionar.
- Exibir o segredo completo somente uma vez, no momento da criação.
- Guardar no banco somente hash seguro da chave, nunca a chave em texto puro. Usar um prefixo identificável, como `sk_live_` e `sk_test_`, sem sugerir que essas chaves são tokens oficiais da Meta.
- Comparar hashes de forma segura e implementar revogação imediata.
- Incluir ambientes de teste e produção se isso puder ser feito com clareza e sem complicar excessivamente o MVP.
- Aplicar rate limit por chave/organização e limites configuráveis.
- Validar autenticação, autorização, esquema de entrada e tamanho do corpo.
- Retornar erros JSON consistentes, com código de erro, mensagem segura e identificador de requisição.
- Criar documentação OpenAPI/Swagger da API própria.
- Não expor tokens oficiais da Meta nem permitir que uma organização use IDs ou canais pertencentes a outra.
- As chaves internas autorizam o uso do serviço; a chamada à Meta deve ser feita pelo backend com a credencial correta do ativo vinculado.

### 4.5 Proxy/encaminhamento de chamadas oficiais
Implemente uma camada de serviço para encaminhar chamadas permitidas à API oficial do WhatsApp Cloud API.

- Começar com endpoints necessários ao MVP: consultar informações básicas de um número conectado, enviar mensagem de texto e consultar o resultado/estado retornado pela Meta quando suportado.
- Use os endpoints, versão de Graph API, campos e formatos atuais confirmados na documentação oficial.
- Enviar sempre os campos obrigatórios da Meta, inclusive `messaging_product` quando exigido.
- Validar o destinatário, conteúdo, tipo de mensagem, ativo associado e autorização do cliente.
- Respeitar janela de atendimento, modelos de mensagem aprovados, consentimento do destinatário, políticas e limites da Meta.
- Não implementar spam, coleta de contatos, evasão de limites ou envio sem autorização.
- Não apresentar “disparo em massa” irrestrito como funcionalidade. Se houver envio a múltiplos destinatários no futuro, deve ser uma fila controlada, com opt-in, templates aprovados quando exigidos, rate limits, auditoria e respeito às políticas.
- Tratar timeouts, erros HTTP, respostas inválidas, limites de taxa e erros da Meta sem vazar tokens ou dados pessoais em logs.
- Usar timeouts explícitos e retries limitados apenas quando seguros. Não repetir automaticamente uma mensagem que possa ser duplicada sem uma estratégia de idempotência.
- Preservar o significado da resposta da Meta e mapear erros para respostas próprias sem esconder o erro original relevante.
- Definir interface/adaptador para suportar outros canais no futuro, sem acoplar todo o código ao WhatsApp.

### 4.6 Webhooks recebidos da Meta
- Criar endpoint público para verificação do webhook usando o mecanismo oficial de challenge/verify token.
- Validar o método, challenge e token de verificação conforme a documentação oficial.
- Validar a assinatura `X-Hub-Signature-256` com HMAC-SHA256 sobre o corpo bruto da requisição e o App Secret, conforme especificação oficial. Comparar de forma constante no tempo.
- Não processar eventos como confiáveis antes de validar a assinatura.
- Tratar mensagens recebidas, status de envio/entrega/leitura/falha e outros eventos relevantes disponíveis para as permissões do app.
- Validar o formato do payload, lidar com eventos desconhecidos e prevenir processamento duplicado com ID de evento/mensagem ou chave de idempotência apropriada.
- Responder rapidamente à Meta com status adequado e transferir processamento pesado para mecanismo de fila simples e confiável quando necessário. Para o MVP no Render, se não houver Redis/fila externa configurada, implemente uma alternativa segura com registro no banco e processamento controlado, sem prometer processamento assíncrono que não exista.
- Registrar eventos com retenção mínima necessária, sem armazenar conteúdo sensível desnecessariamente.
- Documentar a configuração do webhook no painel de desenvolvedor da Meta e os campos/eventos que precisam ser assinados.

### 4.7 Webhooks de saída para os clientes
- Permitir cadastrar URLs HTTPS de webhook por organização.
- Enviar eventos como `message.received`, `message.status.updated`, `channel.connected`, `channel.disconnected` e `api.request.failed` quando esses eventos existirem no sistema.
- Assinar as entregas de saída com HMAC-SHA256 e incluir timestamp e identificador de entrega.
- Implementar timeout, tentativas limitadas com backoff, registro do status e proteção contra repetição indefinida.
- Validar URL e bloquear SSRF: rejeitar localhost, IPs privados, link-local, endereços de metadados de cloud e esquemas diferentes de HTTPS em produção; revalidar redirecionamentos/DNS quando aplicável. Não permitir que clientes usem o servidor como proxy para destinos internos.
- Criar tela para testar webhook e visualizar histórico sem expor segredos.
- Guardar o segredo de assinatura de forma segura e exibi-lo apenas na criação/rotação.

### 4.8 Logs, auditoria e uso
- Registrar chamadas de API com organização, chave identificada sem segredo, endpoint, status, latência, timestamp, request ID e erro sanitizado.
- Não registrar `Authorization`, tokens da Meta, cookies, segredos, conteúdo completo de mensagens ou dados pessoais desnecessários.
- Criar limites de retenção e instruções para limpeza periódica.
- Dashboard com uso real calculado a partir dos registros; não inventar contagens.
- Auditar criação/revogação de chaves, conexão/desconexão de canais e mudanças de webhook.
- Incluir idempotência para operações sensíveis, especialmente envio de mensagens e processamento de webhooks.

## 5. BANCO DE DADOS SUPABASE

Crie um arquivo completo `supabase/schema.sql` com tabelas, chaves estrangeiras, índices, constraints, triggers necessárias, políticas RLS e comentários. Ajuste o esquema conforme a arquitetura real. Considere tabelas equivalentes a:

- `organizations`: empresa/tenant, nome, slug, proprietário e timestamps.
- `organization_members`: associação entre usuário Supabase Auth, organização e papel.
- `meta_connections`: conexão autorizada, canal, IDs de ativos, estado e timestamps.
- `api_keys`: organização, nome, prefixo, hash, ambiente, escopos, última utilização, expiração, revogação e timestamps.
- `webhook_endpoints`: organização, URL, eventos assinados, segredo armazenado com segurança, status e timestamps.
- `webhook_deliveries`: evento, endpoint, tentativas, resposta sanitizada, status, próximo retry e timestamps.
- `webhook_events`: eventos recebidos da Meta, identificador de deduplicação, tipo, payload mínimo necessário e estado de processamento.
- `api_request_logs`: métricas sanitizadas de requisições.
- `audit_logs`: ações relevantes realizadas por usuários ou processos.
- `usage_records`, se necessário, para agregar consumo.

Requisitos de banco:
- UUIDs e timestamps UTC.
- Índices nas colunas consultadas frequentemente.
- Integridade referencial e unicidade para impedir conexões/eventos duplicados.
- RLS habilitada em todas as tabelas que contêm dados de tenants.
- Políticas que garantam isolamento entre organizações.
- Não confiar em `organization_id` enviado pelo navegador: validar associação do usuário no backend e nas políticas.
- Operações administrativas com service role somente no backend, com autorização explícita.
- Nunca colocar a service role key no cliente.
- Incluir instruções claras sobre como executar o SQL no Supabase SQL Editor.
- Se uma função SQL ou trigger exigir privilégios especiais, documente.
- Não criar políticas RLS permissivas como `USING (true)` para dados privados.
- Use migrations adicionais se necessário, mas inclua uma forma clara de instalar o esquema do zero.

## 6. SEGURANÇA E PRIVACIDADE

Implemente as medidas pertinentes, incluindo:
- Configuração de cookies de sessão seguros quando aplicável: `HttpOnly`, `Secure` em produção e `SameSite`.
- Proteção CSRF para formulários e operações baseadas em sessão.
- CORS restrito às origens configuradas.
- Proteção contra XSS, SQL injection e mass assignment; consultas parametrizadas/SDK oficial.
- Validação de entradas com biblioteca apropriada.
- Rate limiting em login sensível, criação de chaves, envio de mensagens e endpoints públicos.
- Headers de segurança e limite de tamanho de requisições.
- Segredos via variáveis de ambiente; nunca commitar `.env`.
- Criptografia de tokens da Meta persistidos, com chave de criptografia dedicada e instruções de rotação. Não usar hash no lugar de criptografia para tokens que precisam ser recuperados.
- Sanitização de logs e mensagens de erro.
- Auditoria e estratégia para revogar tokens/chaves.
- Verificação de assinatura em webhooks.
- Prevenção contra SSRF nos webhooks de saída.
- Política de retenção/exclusão de dados e mecanismo de desconexão.
- Páginas/documentos iniciais de Termos de Uso e Política de Privacidade como modelos editáveis, não como aconselhamento jurídico nem textos finais garantidamente conformes.
- Considerar LGPD: finalidade, minimização, transparência, retenção, exclusão e atendimento a solicitações dos titulares.
- Não armazenar dados pessoais ou conteúdo de mensagens além do necessário ao funcionamento.
- Não incluir PII ou segredos em URLs, logs ou mensagens de erro.

## 12. CONTRATO DE API E EXEMPLOS

Defina endpoints documentados e consistentes. Inclua, conforme implementado, rotas semelhantes a:
- `GET /health`
- `GET /api/v1/me`
- `GET /api/v1/channels`
- `POST /api/v1/whatsapp/{phone_number_id}/messages`
- `GET /api/v1/usage`
- endpoints de gestão de chaves, webhooks e conexões protegidos por sessão e autorização.
- endpoint público de webhook da Meta, com nome/caminho documentado.
- endpoint de callback OAuth.

Não trate a lista acima como prova de que qualquer endpoint Meta específico é válido: esses são endpoints da MINHA aplicação. Os endpoints externos da Meta, parâmetros e versões devem ser conferidos na documentação oficial atual.

Para enviar uma mensagem, documente um formato JSON apropriado ao endpoint próprio, por exemplo:
{
  "to": "55DDDNUMERO",
  "type": "text",
  "text": {
    "body": "Mensagem de teste"
  }
}

Ajuste o payload no adaptador para o formato oficial exigido pela versão atual da Cloud API. Responda com JSON consistente e sem expor token da Meta. Inclua cabeçalho de autenticação com chave interna fictícia apenas como placeholder, por exemplo `Authorization: Bearer sk_test_SUBSTITUA_PELA_SUA_CHAVE`.
